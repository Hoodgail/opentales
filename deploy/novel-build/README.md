# Persistent novel-build acceptance runs

This Compose project runs the existing acceptance script against **two separate PostgreSQL databases and persistent output volumes**. It has no public ports, Traefik routers, fixed container names, production volumes or external networks. Each model has its own network and database. It is intended for a separate Dokploy Compose application, after inspecting capacity and the existing applications. The configured memory ceilings total 4 GiB, in addition to production and image-build requirements.

**Deployment is not yet verified.** On 2026-09-22, the supplied Dokploy host returned HTTP 404 for the authenticated `/api/project.all` request. No staging resources were created. Container deployment and host-restart recovery remain acceptance gates; unit tests and a valid Compose file do not prove them.

## Configure and restore

1. Pin the checkout to the exact PR commit being tested. Set `VALIDATION_REVISION` to that full SHA and verify `git rev-parse HEAD` before building. The image tag, container revision label and run reports record that value; these labels alone do not prove the checkout. Do not point the existing production application at this branch.
2. Supply the values in `.env.example` using Dokploy's private environment settings or a private file outside the repository. Use distinct, URL-safe random database passwords and a staging-only JWT secret. Set the two restored build IDs. Keep `COMPOSE_PROFILES` unset for the initial database deployment. Do not print rendered Compose configuration: it contains the resolved secrets.
3. Start only `gemini-db` and `luna-db`. Build the worker image. Apply the repository migrations to each empty database using the corresponding worker service, without running the validator:

   ```sh
   docker compose -f deploy/novel-build/compose.yml --env-file /private/validation.env up -d gemini-db luna-db
   docker compose -f deploy/novel-build/compose.yml --env-file /private/validation.env --profile acceptance build
   docker compose -f deploy/novel-build/compose.yml --env-file /private/validation.env run --rm --no-deps gemini pnpm exec prisma migrate deploy
   docker compose -f deploy/novel-build/compose.yml --env-file /private/validation.env run --rm --no-deps luna pnpm exec prisma migrate deploy
   ```

4. Restore the corresponding **logical data-only SQL** into each empty, migrated database. PGlite `checkpoint.tar.gz` files are portable PGlite snapshots, not PostgreSQL container data directories. The private checkpoint package contains `checkpoint-data.sql.gz`, migration checksums, and round-trip row fingerprints. Check these before importing. Do not restore over an existing run or import `_prisma_migrations` from the embedded harness. Keep workers stopped throughout the import.

   ```sh
   gzip -dc /private/gemini/checkpoint-data.sql.gz | docker compose -f deploy/novel-build/compose.yml --env-file /private/validation.env exec -T gemini-db psql -X -v ON_ERROR_STOP=1 --single-transaction -U opentales -d opentales_validation_gemini -f -
   gzip -dc /private/luna/checkpoint-data.sql.gz | docker compose -f deploy/novel-build/compose.yml --env-file /private/validation.env exec -T luna-db psql -X -v ON_ERROR_STOP=1 --single-transaction -U opentales -d opentales_validation_luna -f -
   ```

   These commands assume the checkpoints have no external assets yet. If resuming a later run with exports/uploads, restore its `assets` directory to the matching `/validation/assets` volume as well. PostgreSQL 18 is used because the current logical dumps were generated by PostgreSQL 18.3.

5. Verify the imported run IDs, task counts, current manuscript heads and token/cost totals against the checkpoint evidence. Then enable the `acceptance` profile and start `gemini` and `luna`. Use this profile for subsequent Dokploy deployments. Keep the Compose project name stable so its volumes remain attached.

## Restart and observe

- The validator persists `run-id.txt` and resumes it after a process restart. Explicit IDs must match any saved ID. This deployment requires an existing ID and refuses to create a replacement story. Startup rehydrates the fixture's provider key using the staging encryption secret.
- An unchanged token limit no longer reauthorizes a paused run on every restart. A changed `LIVE_MAX_TOKENS` is an explicit authorization update; review it before applying. Provider limits and the stored monetary budget still apply. Restarts do not automatically raise either budget.
- `heartbeat.json` refreshes every 30 seconds during model calls. It includes revision, completed tasks, active task attempts and provider retry deadlines. `report.json` records sweep results. Check its timestamp and container state together; an old heartbeat does not imply a running worker.
- Unexpected process failures restart up to three times. A persisted `PAUSED`, `FAILED` or `CANCELLED` status stops the supervised container with exit code zero **without claiming success**. Inspect the report and resolve the actual blocker before restarting. `verification.json` is produced only after a completed build passes all manuscript/export assertions.
- The worker's `on-failure` policy does not start it automatically after a Docker daemon restart. After host maintenance, start the same Compose services again and verify their saved run IDs. The databases use `unless-stopped`; their data and worker output remain in named volumes. Fully automatic host-reboot startup is not established by this staging configuration.
- SIGTERM requests a stop at the next task boundary. Docker allows two minutes, then may terminate the process. The normal database lease and stale-attempt recovery handle an interrupted task on restart. Accepted prior tasks remain persisted. An unfinished API call may have incurred provider usage that cannot be recovered exactly.
- Demonstrate restart with both model workers active, confirm the same build IDs resume without duplicate scenes or lost accepted work, and then check both `verification.json` files and downloaded manuscripts. This demonstration has not yet run on Dokploy.

Do not delete volumes to fix an error. Stop the affected worker, preserve its database and output, diagnose the task/trace, fix and test the code, then resume through normal build recovery. A human-reviewed completed manuscript from each provider remains required before declaring full-length readiness.
